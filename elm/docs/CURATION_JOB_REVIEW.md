# r18: durable curation result review, production dispatch unavailable

## What is usable and what remains unavailable

This milestone adds authenticated current-private-chat job inspection and individually confirmed proposal acceptance into a pending record. Real model-assisted extraction is still unavailable. The internal qualification workflow can send only through the exact private r17 loopback test adapter; it is not registered as a plugin RPC or model tool. No public endpoint accepts fake model responses or creates fabricated jobs. Public curation dispatch still refuses; no credential is read and no live route is enabled.

The native PluginLlm facade still resolves dynamic provider/task settings and auxiliary credential pools/endpoints, with fallback/retry behavior. Those mechanisms do not establish a reviewed immutable recipient-to-credential binding. Ambient main-provider credentials are not copied into this workflow. A future dedicated host-owned credential slot must bind the exact endpoint/origin/path, model, provider, profile and credential version, and revalidate that binding before any I/O. This document does not claim that capability exists.

## Qualified local workflow

`elm_plugin.curation_jobs._qualification_workflow(transport, ledger)` accepts only the exact private `_LoopbackTransport` and `AttemptLedger` types. It uses real private source snapshots and the real native owner/read/publication fences. `prepare(source_ids, model='offline-test')` returns the complete immutable candidate body including model, recipient, SHA-256, opaque token and expiry. At most four selected sources are included; source and payload bounds remain those of r15/r17. The preview is only a local test recipient, not a price quote or real-provider consent.

`execute(preview_token, confirm=True)` consumes the preview and writes an `attempted` job in the private manifest before invoking the host's one-use durable contract. Exact owner/store/source state, hashes, sensitivity and current native scope are revalidated. A read-only preflight diagnoses an already-withdrawn source before entering publication; an intervening race can still produce a native uncertain-outcome error, so this is not a universal no-effects guarantee. The r17 ledger separately durably claims the attempt before transport, and checks freshness again afterward. No native lock spans transport. A revoke/withdraw after actual admission cannot retract bytes already sent; it can block publication and later acceptance.

Only strict, bounded exact-excerpt proposals are persisted after response validation against the selected sources. Arbitrary raw model output is not retained in this job registry. Unknown fields, hallucinated citations, altered spans/digests, scope/state/sensitivity overrides and mismatched provenance are refused. Titles remain unverified model labels. Assistant-source excerpts remain source-document references, not authenticated user facts. Sensitivity is inherited and cannot be lowered through acceptance. Nothing is automatically approved.

Precommit failure during result validation, source freshness checks or saving leaves the job `attempted` with no usable proposals. A postcommit native fence failure or lost reply can instead report an unconfirmed outcome even though a `ready` result is already persisted. Always inspect job list/get; never infer persisted state solely from an error or resend automatically. An observed `attempted` state means no confirmed usable result, not proof that no request was sent or no response received. There is no retry/resume/send-on-restart operation. Cross-store job/attempt-ledger commits are not atomic: a job can exist without a ledger claim, or a completed ledger response can have no saved result. All such gaps require reconciliation, never automatic resend. A successful result becomes `ready`, revision 2; the job retains accepted indexes as later revisions advance.

Internal previews expire after 300 monotonic seconds, are capped at 16 and are cleared on close. `cancel(preview_token)` removes an owned unexecuted preview. Cancel/close serialize behind an already executing synchronous workflow; they do not interrupt or retract in-flight bytes. There is no public cancel-running-job endpoint because there is no production dispatcher.

## Public review API

- `private.curation.jobs.list({limit?, before?})`: current-chat summaries only, default/max 16, opaque job-ID cursor, `jobs` and `next_before`. Summary fields: job_id, revision, state, created_at, proposal_count, accepted_indexes.
- `private.curation.jobs.get({job_id})`: `{job: summary + proposals + accepted_records + recipient + model + payload_sha256, inspection_only: true, content_role: 'untrusted_model_proposals'}`. Proposals include complete text, exact citations, sensitivity and source-origin labels. The full serialized reply is capped at 64 KiB; it is refused rather than truncated. Withdrawn-source results remain inspectable.
- `private.curation.jobs.accept({job_id, proposal_index, expected_revision, confirm:true})`: returns `{record, job}`. Requires current canonical owner/store, exact current source pins, ready job, unconsumed index and matching revision. The array index selects the fully reviewed immutable proposal. The pending record and accepted-index marker are saved atomically in the same manifest. A postcommit error or lost reply can still leave both persisted; reconcile get.job.accepted_records before doing anything else, never retry blindly. Replay or concurrent double acceptance cannot create a second record. Normal separate private-record approval remains required afterward.

All endpoints use authenticated host context, never caller root/profile/session selectors as authority. Human-review RPCs are a protocol for trusted authenticated clients, not proof a human physically clicked. No model tool or automatic recall path invokes these endpoints. Stored result ownership is stable profile/principal/canonical-chat identity; preview/execution uses the complete current native owner snapshot. A fresh valid native scope is still required after a restart; private project selection/catalog fences continue to apply.

## Retention and bounds

The additive `private_curation` schema is validated on every manifest load and before writes. Validation checks stored proposal fields, exact current immutable source contents/hash/span and source role/sensitivity, while allowing source withdrawal to leave review history readable. Withdrawal blocks future acceptance. Already accepted records participate in existing tracked source withdrawal/dependent invalidation.

At most 16 retained jobs exist per principal store, with up to four proposals each. The same exact 4 MiB private-manifest cap includes sources, records, recovery envelopes and job results; capacity failure refuses changes, never silently evicts. Pending record capacity remains 512 active/retained records. No job purge/erasure, automatic migration, project copying or cross-principal sharing is implemented. Lost-success responses can be reconciled through job list/get, accepted_indexes and the accepted_records index-to-record-ID map without resending or reaccepting.

Validated results may contain sensitive text and are stored in the same local plaintext manifest as private memory. There is no new encryption claim. They may duplicate retained source excerpts. Existing filesystem protections reject known redirects but are not a hostile-local-owner sandbox. A future real credentialed route, exact monetary authorization, durable job recovery policy and qualified provider response envelope remain separate blockers to live use.
